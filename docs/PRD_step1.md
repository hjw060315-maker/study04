# PRD 1단계: 냉장고 사진 입력과 식재료 인식

> **구현 방식 변경 (Streamlit)**: 이 앱은 Streamlit으로 개발해 Streamlit Community Cloud에 무료 배포한다. 따라서 아래 8절의 `POST /api/ingredients`와 7절의 HTML 화면은 쓰지 않고, 같은 기능을 Streamlit 위젯(`st.file_uploader`, `st.camera_input`, `st.data_editor`)으로 구현했다. 이미지 축소는 브라우저가 아니라 서버(Pillow)에서 하고, 오류 코드(`invalid_image`, `too_large`, `model_unavailable`, `parse_failed`)는 `AppError`로 유지한다. API 키는 `st.secrets`(Secrets)에서 읽는다. 추가로 무료 모델 한도 보호를 위해 세션당 10회/시간, 서버 전체 60회/시간의 호출 제한을 둔다. 또한 1순위 모델이 막히면 한 번 더 시도한 뒤 폴백 모델로 자동 전환한다.

## 1. 배경과 목표

냉장고 안에 어떤 재료가 있는지 사용자가 직접 입력하는 것은 번거롭다. 1단계는 **냉장고 사진 한 장을 올리면 식재료 목록을 자동으로 만들어 주는 것**이 목표이다. 이 결과는 2단계(레시피 생성)의 입력이 된다.

**성공 기준**
- 사진 업로드부터 재료 목록 표시까지 한 화면에서 끝난다.
- 사진에 뚜렷이 보이는 재료의 대부분(목표 70% 이상)이 목록에 포함된다.
- 인식이 틀려도 사용자가 목록을 쉽게 고칠 수 있다.

## 2. 범위

**포함**
- 이미지 업로드(파일 선택, 드래그 앤 드롭, 모바일 카메라 촬영)
- 비전 모델 호출과 식재료 목록 추출
- 인식 결과 확인·수정(추가, 삭제, 이름 변경)
- 오류·로딩 상태 처리

**제외**
- 레시피 생성(2단계), 로그인·저장(3단계)
- 재료 수량·유통기한의 정밀 인식(수량은 모델이 추정한 대략값만 표시)
- 영상, 여러 장 동시 업로드

## 3. 사용자와 시나리오

- 사용자: 냉장고 재료로 뭘 만들지 고민하는 일반 사용자(주로 모바일).
- 시나리오: 냉장고를 열고 사진을 찍어 올린다 → 몇 초 뒤 "계란, 양파, 우유, 김치…" 목록이 뜬다 → 틀린 항목을 고치고 다음 단계로 간다.

## 4. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F1-1 | 사용자는 JPG, PNG, WEBP 이미지를 업로드할 수 있다. | 필수 |
| F1-2 | 업로드 전에 미리보기를 보여 주고, 다른 사진으로 교체할 수 있다. | 필수 |
| F1-3 | 서버가 이미지를 `nvidia/nemotron-3.5-super-vl:free` 모델에 보내 식재료를 인식한다. | 필수 |
| F1-4 | 모델 응답은 JSON 형식의 재료 목록으로 변환해 화면에 보여 준다. | 필수 |
| F1-5 | 사용자는 재료를 추가, 삭제, 이름 수정할 수 있다. | 필수 |
| F1-6 | 인식에 실패하거나 재료가 없으면 이유를 안내하고 다시 시도할 수 있다. | 필수 |
| F1-7 | 재료가 아닌 것(용기, 선반 등)은 목록에서 제외한다. | 권장 |
| F1-8 | 모바일에서 카메라로 바로 촬영할 수 있다. | 권장 |

## 5. 모델 호출 설계

- **모델**: `nvidia/nemotron-3.5-super-vl:free` (OpenRouter `/chat/completions`)
- **입력**: 이미지를 base64 data URL로 보낸다. 앞서 `test_api.py`에서 같은 방식으로 정상 동작을 확인했다.
- **프롬프트 요지**: "냉장고 사진에서 식재료만 찾아 한국어로 JSON 배열로만 답하라. 항목은 `name`(재료명), `quantity`(대략적 수량, 모르면 null)이다. 재료가 아닌 것은 넣지 말고, 확실하지 않으면 넣지 마라."
- **출력 예시**
  ```json
  {"ingredients": [{"name": "계란", "quantity": "6개 정도"}, {"name": "양파", "quantity": null}]}
  ```
- **후처리**: 응답에서 JSON을 추출해 검증하고, 형식이 깨졌으면 한 번 재시도한 뒤 실패로 처리한다. 재료명은 공백 제거와 중복 병합을 한다.
- 모델 응답에 `reasoning` 필드가 함께 올 수 있으므로 `content`만 사용한다.

## 6. 비기능 요구사항

- **보안**: `OPENROUTER_API_KEY`는 서버에서만 읽는다(`config.py`의 `get_api_key()` 재사용). 브라우저로 키를 내려보내지 않고, 키를 로그에 남길 때는 `mask()`를 쓴다.
- **이미지 제한**: 파일 크기 상한(예: 10MB)과 형식을 서버에서 검증한다. 큰 사진은 브라우저에서 긴 변 1280px 정도로 줄여서 올려 전송량과 응답 시간을 줄인다.
- **성능**: 일반적인 사진 기준으로 업로드부터 결과 표시까지 30초 이내를 목표로 하고, 진행 중 상태를 보여 준다.
- **개인정보**: 업로드한 사진은 인식에만 쓰고 서버에 저장하지 않는다. 사용자에게 이 사실을 화면에 알린다.
- **무료 모델 제약**: `:free` 모델은 404, 429 같은 제공자 오류가 잦다. 한 번 자동 재시도하고, 그래도 실패하면 "잠시 후 다시 시도해 주세요"를 안내한다.

## 7. 화면 구성

1. 업로드 영역: 사진 선택·촬영 버튼, 미리보기
2. "재료 인식하기" 버튼과 로딩 표시
3. 인식 결과: 재료 칩(chip) 목록, 각 칩에 삭제 버튼, 재료 추가 입력창
4. "레시피 추천받기" 버튼(2단계로 이동, 재료가 1개 이상일 때만 활성화)

## 8. API 초안

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/ingredients` | 이미지 파일을 받아 `{ingredients: [...]}` 반환 |

오류 응답은 `{error: {code, message}}` 형식으로 통일한다(`invalid_image`, `too_large`, `model_unavailable`, `parse_failed`).

## 9. 수용 기준

- 재료가 보이는 냉장고 사진을 올리면 재료 목록이 표시된다.
- 재료가 없는 사진이나 흐린 사진에서도 화면이 깨지지 않고 안내 문구가 나온다.
- 지원하지 않는 형식과 용량 초과 파일은 서버 호출 전에 거절된다.
- 브라우저 개발자 도구의 네트워크 탭과 소스에서 API 키가 보이지 않는다.
- 사용자가 수정한 목록이 그대로 다음 단계의 입력으로 넘어간다.

## 10. 열린 질문과 가정

- 기술 스택 가정: 기존 코드(Python, `config.py`)를 이어 쓰기 위해 Python 서버(FastAPI 등)와 순수 HTML/JS 프런트엔드를 쓴다. 변경이 필요하면 구현 전에 정한다.
- 인식 정확도 목표(70%)는 임시 값이다. 실제 사진 10장 정도로 측정한 뒤 조정한다.
- 영어 재료명이나 가공식품 브랜드명을 한국어로 정규화할지는 아직 정하지 않았다.
