# PRD 3단계: 사용자 프로필과 레시피 저장

## 1. 배경과 목표

마음에 든 레시피를 나중에 다시 보려면 저장 공간과 사용자 구분이 필요하다. 3단계는 **사용자 프로필을 만들고, 2단계에서 생성한 레시피를 프로필에 저장·조회·삭제**할 수 있게 한다.

**성공 기준**
- 사용자가 프로필을 만들고 다시 접속해도 저장한 레시피가 남아 있다.
- 레시피 상세 화면에서 한 번의 클릭으로 저장된다.
- 한 사용자의 데이터가 다른 사용자에게 보이지 않는다.

## 2. 범위

**포함**
- 회원가입, 로그인, 로그아웃
- 프로필(닉네임, 선호·제외 재료) 관리
- 레시피 저장, 목록, 상세, 삭제
- 저장 목록 검색·정렬 기본 기능
- 프로필의 제외 재료를 2단계 조건에 자동 반영

**제외**
- 소셜 로그인, 이메일 인증, 비밀번호 찾기(후속 과제)
- 레시피 공유·공개, 댓글
- 저장한 레시피의 수정(저장 시점의 내용을 그대로 보관)
- 결제, 알림

## 3. 사용자와 시나리오

- 처음 쓰는 사용자: 레시피가 마음에 들어 "저장"을 누른다 → 로그인 안내가 뜬다 → 가입 후 방금 보던 레시피가 저장된다.
- 재방문 사용자: 로그인한다 → "내 레시피"에서 저장한 목록을 본다 → 하나를 열어 조리 순서를 확인하거나 삭제한다.
- 프로필에 알레르기·비선호 재료를 등록해 두면, 다음 추천부터 자동으로 제외된다.

## 4. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F3-1 | 사용자는 아이디(또는 이메일)와 비밀번호로 가입하고 로그인할 수 있다. | 필수 |
| F3-2 | 비밀번호는 해시(bcrypt 또는 argon2)로만 저장한다. | 필수 |
| F3-3 | 프로필에 닉네임과 제외 재료 목록을 설정하고 수정할 수 있다. | 필수 |
| F3-4 | 2단계 레시피 상세 화면의 "저장" 버튼으로 레시피를 내 프로필에 저장한다. | 필수 |
| F3-5 | "내 레시피" 화면에서 저장 목록을 최신순으로 보고, 상세를 열고, 삭제할 수 있다. | 필수 |
| F3-6 | 이미 저장한 레시피를 다시 저장하려 하면 중복 저장 대신 안내를 보여 준다. | 권장 |
| F3-7 | 저장 목록을 이름·재료로 검색할 수 있다. | 권장 |
| F3-8 | 프로필의 제외 재료가 2단계 요청 조건에 기본값으로 채워진다. | 권장 |
| F3-9 | 비로그인 상태에서도 1~2단계는 사용할 수 있고, 저장 기능만 로그인을 요구한다. | 필수 |
| F3-10 | 회원 탈퇴 시 계정과 저장 데이터를 모두 삭제한다. | 권장 |

## 5. 데이터 설계

저장소는 파일 기반 SQLite를 기본으로 한다(소규모 서비스, 별도 DB 서버 불필요).

**users**
| 컬럼 | 설명 |
|---|---|
| id | 기본 키 |
| username | 고유 값 |
| password_hash | 해시된 비밀번호 |
| nickname | 표시 이름 |
| excluded_ingredients | 제외 재료(JSON 배열) |
| created_at | 가입 시각 |

**saved_recipes**
| 컬럼 | 설명 |
|---|---|
| id | 기본 키 |
| user_id | users.id (외래 키, 삭제 시 함께 삭제) |
| title | 레시피 이름(검색용) |
| content | 2단계 레시피 JSON 전체 |
| source_ingredients | 저장 당시 재료 목록(JSON) |
| created_at | 저장 시각 |

사용자당 `(user_id, title)` 중복을 방지한다. 사진 원본은 저장하지 않는다(1단계 정책 유지).

## 6. API 초안

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/auth/signup` | 가입 |
| POST | `/api/auth/login` | 로그인(세션 쿠키 발급) |
| POST | `/api/auth/logout` | 로그아웃 |
| GET / PUT | `/api/profile` | 프로필 조회·수정 |
| POST | `/api/saved-recipes` | 레시피 저장 |
| GET | `/api/saved-recipes?q=` | 내 저장 목록(검색 가능) |
| GET | `/api/saved-recipes/{id}` | 상세 |
| DELETE | `/api/saved-recipes/{id}` | 삭제 |
| DELETE | `/api/account` | 회원 탈퇴 |

저장 관련 API는 모두 로그인이 필요하고, 항상 **현재 로그인한 사용자의 데이터만** 조회·변경한다. 다른 사용자의 id로 접근하면 404로 응답한다.

## 7. 비기능 요구사항

- **보안**
  - 세션은 `HttpOnly`, `SameSite` 쿠키로 관리하고, 상태를 바꾸는 요청에는 CSRF 대책을 둔다.
  - 가입·로그인 시도 횟수를 제한한다.
  - 비밀번호 최소 길이(8자 이상)를 검증한다.
  - 쿼리는 파라미터 바인딩만 사용한다.
  - 프로필·레시피 텍스트는 화면에 출력할 때 이스케이프한다.
- **개인정보**: 수집 항목은 아이디, 닉네임, 제외 재료, 저장 레시피로 최소화한다. 탈퇴 시 전부 삭제한다.
- **API 키 분리**: `OPENROUTER_API_KEY`는 계속 서버 환경에서만 읽는다. 사용자별 키 입력은 받지 않는다.
- **무료 모델 비용·한도**: 비로그인 사용도 허용하므로, 한도 보호를 위해 IP 또는 세션 단위 호출 횟수 제한을 둔다.
- **백업**: SQLite 파일은 `.gitignore`에 추가해 저장소에 올라가지 않게 한다.

## 8. 화면 구성

1. 로그인·가입 화면
2. 프로필 화면: 닉네임, 제외 재료 편집, 로그아웃, 회원 탈퇴
3. 2단계 상세 화면의 "저장" 버튼(비로그인 시 로그인 유도)
4. "내 레시피" 목록: 카드, 검색창, 삭제 버튼
5. 저장 레시피 상세: 재료와 조리 순서

## 9. 수용 기준

- 가입 후 레시피를 저장하고, 로그아웃·재로그인해도 목록에 남아 있다.
- 사용자 A가 저장한 레시피는 사용자 B의 목록과 직접 URL 접근에서 모두 보이지 않는다.
- DB를 열어 봐도 비밀번호가 평문으로 보이지 않는다.
- 같은 레시피를 두 번 저장하면 중복 생성되지 않는다.
- 비로그인 상태에서 저장을 시도하면 로그인 화면으로 안내되고, 로그인 후 저장이 이어진다.
- 프로필에 제외 재료를 등록하면 다음 레시피 요청 조건에 자동으로 들어간다.
- 회원 탈퇴 후 해당 계정의 저장 데이터가 DB에 남지 않는다.

## 10. 열린 질문과 가정

- 인증 방식은 우선 자체 아이디·비밀번호 + 세션 쿠키로 가정했다. 소셜 로그인으로 바꿀지는 정해야 한다.
- 프로필 이름 외 식단 목표(다이어트 등), 가족 인원수 같은 항목을 넣을지는 아직 정하지 않았다.
- 배포 환경(로컬 실습용 또는 외부 공개)에 따라 HTTPS, 계정 보호 수준을 다시 정해야 한다. 외부 공개 시에는 이메일 인증과 비밀번호 재설정이 필요하다.
