# PRD 2단계: 식재료 기반 레시피 생성

## 1. 배경과 목표

1단계에서 확인한 식재료 목록으로 **지금 바로 만들 수 있는 레시피를 추천**한다. 사용자가 "오늘 뭐 먹지?"를 고민하는 시간을 줄이는 것이 목표이다.

**성공 기준**
- 재료 목록과 선택 조건만 정하면 한 번의 요청으로 레시피 여러 개가 나온다.
- 추천 레시피가 사용자가 가진 재료를 최대한 활용한다.
- 부족한 재료는 따로 표시되어, 사용자가 추가 구매가 필요한지 바로 알 수 있다.

## 2. 범위

**포함**
- 1단계 재료 목록을 입력으로 받는 레시피 생성
- 선택 조건: 인원수, 조리 시간, 식사 종류, 제외할 재료(알레르기·비선호)
- 레시피 카드 목록과 상세 보기
- 오류·로딩 상태 처리, 다시 생성하기

**제외**
- 이미지 인식(1단계), 로그인·레시피 저장(3단계)
- 영양소 계산, 칼로리 정밀 산출
- 레시피 사진 생성

## 3. 사용자와 시나리오

- 1단계에서 확인한 재료 목록이 넘어온다 → 인원수와 조리 시간을 고른다 → "레시피 만들기"를 누른다 → 3개 안팎의 추천이 카드로 나온다 → 마음에 드는 카드를 눌러 조리 순서를 본다.

## 4. 기능 요구사항

| ID | 요구사항 | 우선순위 |
|---|---|---|
| F2-1 | 1단계의 최종 재료 목록(수정 반영본)을 입력으로 받는다. | 필수 |
| F2-2 | 서버가 `nvidia/nemotron-3.5-lightning:free` 모델로 레시피를 생성한다. | 필수 |
| F2-3 | 한 번에 레시피 3개를 생성하고 카드 목록으로 보여 준다. | 필수 |
| F2-4 | 각 레시피는 이름, 한 줄 설명, 조리 시간, 난이도, 인원수, 재료 목록, 조리 순서를 포함한다. | 필수 |
| F2-5 | 재료는 "보유 재료"와 "추가로 필요한 재료"를 구분해 표시한다. | 필수 |
| F2-6 | 인원수, 최대 조리 시간, 식사 종류(아침, 점심, 저녁, 간식)를 조건으로 줄 수 있다. | 권장 |
| F2-7 | 제외할 재료를 지정하면 그 재료가 들어간 레시피는 나오지 않는다. | 권장 |
| F2-8 | "다시 추천받기"로 다른 레시피를 새로 생성할 수 있다. | 권장 |
| F2-9 | 생성에 실패하면 이유를 안내하고 재시도할 수 있다. | 필수 |

## 5. 모델 호출 설계

- **모델**: `nvidia/nemotron-3.5-lightning:free` (OpenRouter `/chat/completions`, 텍스트 전용)
- **입력**: 재료 목록(이름, 대략적 수량)과 선택 조건을 프롬프트에 넣는다.
- **프롬프트 요지**: "당신은 요리 전문가다. 아래 재료를 최대한 활용하는 한국어 레시피 3개를 JSON으로만 답하라. 기본 양념(소금, 설탕, 간장, 식용유, 후추 등)은 보유한 것으로 간주한다. 목록에 없는 재료는 `missing_ingredients`에 따로 적고, 제외 재료는 쓰지 마라."
- **출력 형식(JSON)**
  ```json
  {"recipes": [{
    "title": "계란 양파 볶음밥",
    "summary": "남은 밥과 계란으로 10분 만에 만드는 한 끼",
    "servings": 2,
    "time_minutes": 15,
    "difficulty": "쉬움",
    "ingredients": [{"name": "계란", "amount": "2개", "have": true}],
    "missing_ingredients": ["대파"],
    "steps": ["양파를 잘게 썬다.", "..."]
  }]}
  ```
- **후처리**: 응답에서 JSON을 추출해 필드를 검증한다. 형식이 깨졌으면 한 번 재시도하고 그래도 안 되면 실패로 처리한다. 모델 응답의 `reasoning` 필드는 버리고 `content`만 쓴다.
- **환각 방지**: 사용자 재료에 없는 것은 반드시 `have: false`로 구분하도록 지시하고, 서버에서 재료명 비교로 한 번 더 확인한다.

## 6. 비기능 요구사항

- **보안**: API 키는 서버에서만 사용한다(`config.py`의 `get_api_key()`). 사용자 입력(재료명, 제외 재료)은 프롬프트에 넣기 전에 길이를 제한하고, 입력이 모델 지시를 바꾸지 못하도록 데이터 영역으로 구분해서 전달한다.
- **성능**: 요청부터 결과 표시까지 30초 이내를 목표로 하고, 진행 중 상태를 보여 준다. 응답 지연이 크면 레시피 개수를 줄이는 옵션을 고려한다.
- **안전 안내**: 알레르기 정보는 모델 판단에 의존하므로 화면에 "알레르기는 직접 확인하세요" 안내를 둔다.
- **무료 모델 제약**: `:free` 모델은 404, 429가 잦다. 자동 재시도 1회 후 실패하면 안내 문구를 보여 준다.

## 7. 화면 구성

1. 재료 요약: 1단계에서 넘어온 재료 칩(여기서도 추가·삭제 가능)
2. 조건 입력: 인원수, 조리 시간, 식사 종류, 제외 재료
3. "레시피 만들기" 버튼과 로딩 표시
4. 결과: 레시피 카드(이름, 설명, 시간, 난이도, 부족 재료 개수)
5. 상세 보기: 재료(보유·부족 구분)와 조리 순서. 3단계가 붙으면 여기에 "저장" 버튼이 들어간다.

## 8. API 초안

| 메서드 | 경로 | 설명 |
|---|---|---|
| POST | `/api/recipes` | `{ingredients, servings, max_minutes, meal_type, exclude}`를 받아 `{recipes: [...]}` 반환 |

오류 응답은 1단계와 같은 `{error: {code, message}}` 형식을 쓴다(`empty_ingredients`, `model_unavailable`, `parse_failed`).

## 9. 수용 기준

- 재료 3개 이상으로 요청하면 레시피 3개가 카드로 나오고, 각 카드에 필수 필드가 모두 있다.
- 부족한 재료가 보유 재료와 구분되어 표시된다.
- 제외 재료로 지정한 재료가 어떤 레시피에도 나오지 않는다.
- 재료가 비어 있으면 요청이 서버 호출 전에 거절된다.
- 모델이 형식이 깨진 응답을 줘도 화면이 깨지지 않고 재시도 안내가 나온다.

## 10. 열린 질문과 가정

- 기본 양념 목록의 범위(소금, 간장 등)는 임시로 정했다. 실제 결과를 보고 조정한다.
- 레시피 3개를 한 번에 요청할 때 응답 길이와 속도가 문제되는지 구현 초기에 측정한다.
- 같은 재료로 반복 요청할 때 결과 다양성을 높일지(예: 무작위 시드, 이전 추천 제외)는 정하지 않았다.
